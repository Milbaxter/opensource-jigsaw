# Render-aware texture allocation — prospective protocol draft

Status: **NOT YET FROZEN; no encoding, rendering or performance evaluation has occurred.** This document proposes a bounded integration experiment. The parent must publish/freeze the final protocol before execution. Clarifications before that freeze are not post-result changes.

## Claim and limits

Can joint rendered-error allocation select per-texture standard texture encodings with materially better held-out rendered fidelity than competent presets and render-aware greedy allocation under the same GLB-byte ceiling and configuration-evaluation budget?

Business hypothesis: a web 3D production agency could use a reproducible, local batch export and acceptance packet when preparing customer product catalogs. Primary measured outcomes are real deliverable bytes and image error in a named browser renderer. Neither metric establishes human-perceived equivalence, customer savings, runtime speed, cross-device fidelity, or superiority to untested paid software.

## Frozen inputs and exclusion

Use only FlightHelmet, ToyCar, WaterBottle and BoomBox from KhronosGroup/glTF-Sample-Assets commit `c6a6bd13ab2b3c685c7903d03561b8a9392f38b8`, original `Models/<name>/glTF/` files. Source glTF JSON hashes are already in `input-schema.json`; download/hash referenced buffers/images before any rendering. Preserve per-model CC0 license/attribution. Do not use DamagedHelmet. Do not add another asset after results.

Geometry, node hierarchy, UVs, material scalars, texture bindings, sampler modes and animations remain unchanged. Deduplication, mesh quantization/simplification and topology changes are excluded. Images shared across material slots remain shared; a texture used in incompatible color-space roles is retained unmodified and reported rather than guessed. Unsupported extensions or decoder failures fail the affected asset, without substitution.

Budgets are **1,000,000; 2,000,000; 5,000,000 bytes** of the final standalone GLB, including JSON, geometry, KTX data and alignment. These correspond to cited 1–2MB requests and the Khronos product-asset guideline's 5MB recommendation, not budgets chosen after observing gains. FlightHelmet/ToyCar have source nontexture buffers exceeding 2MB; the four resulting small-budget cells are expected infeasible negative cases. An algorithm must return infeasible, never remove geometry or exceed the ceiling. All 12 cells remain reported.

## Actual encodings and runtime

Prospective package pins: glTF Transform core/functions/extensions/CLI 4.5.0; Three.js 0.186.0; Playwright 1.63.0; Sharp 0.35.4; KTX-Software 4.4.2 Darwin arm64 official release. Preserve release/package hashes, actual dependency lock, licenses, Chrome version and renderer backend before experiment. Existing Google Chrome is available. Unpack the official KTX installer locally; no system installation is necessary. If the version cannot run, record failure and return for a prospectively frozen amendment before measuring alternatives. WebP is explicitly included because the buyer claim concerns delivery bytes, not a stipulated GPU-memory ceiling. KTX failures are reported; they are not silently replaced by WebP.

For every unique source image, prepare ten options: unchanged original; WebP quality 80 at original/half/quarter dimensions; ETC1S at original/half/quarter dimensions, quality 128, compression level 1; UASTC at original/half/quarter dimensions, level 1, Zstandard level 18. Resize with Sharp Lanczos3. For KTX, round each requested dimension down to a positive multiple of 4 (minimum 4); if an original dimension is below 4, omit KTX options for that image rather than upscaling. WebP dimensions are floored with minimum 1. Never upscale. Assign sRGB transfer metadata to base-color/emissive and linear metadata to data maps without converting stored data-map channel values. KTX orientation must be rd or omitted, swizzle identity, DFD primaries/transfer correct, alpha non-premultiplied, and KHR_texture_basisu required when no PNG fallback exists. WebP uses EXT_texture_webp as required. Color resize/mip generation follows the pinned encoder color-space behavior; data channels remain raw linear values. For tangent-space normal images, normalize decoded XYZ vectors after resizing each mip and preserve alpha; exact routine must be frozen and tested on an asymmetric normal control before any real reference render. Every method receives the identical finite option files. Preserve alpha; use ordinary tools and the explicitly specified normal-map handling only. Record actual commands. Use mipmaps for every compressed option and preserve original sampler rules. If the source sampler does not use mipmaps, retain that sampler; stored but unused mip levels still count toward bytes. Remove byte-identical options only; no outcome-based pruning of encodings.

Three.js GLTFLoader/KTX2Loader must decode/transcode the delivered KTX2 in Chrome and render it using actual material shaders. Record supported GPU compression extensions and each resulting internal format. The same backend renders originals and outputs. Encoding each unique option is common preprocessing, timed and charged equally to all methods. Cache files by image/option hash. Report preprocessing time, render calls, selection time and total cost; no speed claim is planned.

## Views, lighting and metric

Render 512×512, pixel ratio 1, no antialiasing, transparent background composited on constant sRGB 0.18 gray, no shadows, exposure 1, ACES tone mapping, sRGB output. Freeze the exact renderer setup and camera-fitting code before any asset reference render. Use a bounding sphere from original world-space geometry, centered at its center, perspective FOV 35 degrees, camera distance `radius / sin(17.5 degrees) * 1.15`, near/far derived from this sphere. Camera looks at the center. Use original model orientation without hand adjustments.

Selection views: azimuths 0,60,120,180,240,300 degrees; elevation 20 degrees. Selection lighting: a PMREM environment generated from the pinned Three.js `RoomEnvironment` example (intensity 1, rotation zero), ambient white intensity 0.5, and directional white intensity 3 from normalized (1,2,3). The environment prevents metallic materials from becoming an uninformative dark special case. The original and every variant share the identical environment map. Evaluate these six images for every configuration. All algorithms see the same views and metric.

Held-out views: azimuths 30,90,150,210,270,330 degrees; elevation 5 and 40 degrees, producing 12 views. Evaluate each with (A) selection lighting and (B) the same PMREM environment rotated 90 degrees around Y, ambient white 0.5, and directional white intensity 3 from normalized (-3,1,-2), producing **24 held-out images per final output**. Do not render held-out views/lights until every method's choices for all four assets and budgets are sealed. These are prospectively withheld views, not an independent customer asset population.

Primary error: mean absolute sRGB channel difference on pixels where the original foreground alpha exceeds 0.01, after compositing both images on the same gray background. Average the three absolute channel errors and divide by 255. Primary selection loss is the maximum mean error across the six selection views, preventing a good average from hiding one bad view. Report mean and maximum held-out view error, plus the 95th percentile per-pixel error as a secondary diagnostic. Alpha mask and reference come only from the unchanged original. Treat an empty foreground mask as a setup failure. This numerical fidelity proxy is not a human perceptual rating.

## Algorithms and equal-budget comparison

All methods may share the source/encoded option files and deterministic original references. A rendered configuration costs six images, even if a cache makes replay cheap. Each search method receives **256 distinct six-view configuration evaluations per asset per byte budget**; repeated configurations count once within that method. The same configuration evaluated by multiple methods counts toward each method's allowance. Each search receives identical preset candidates, but their evaluations count within its 256 allowance. No method sees another's adaptive results, and held-out images never guide selection. Wall time is separately reported; equal calls are not a claim of equal CPU/GPU time.

1. **Channel-aware preset sweep:** all combinations of one resolution fraction for color images and one for noncolor images (three each), with ETC1S color/UASTC noncolor; plus uniform all-ETC1S, all-UASTC and all-WebP at each fraction, a WebP-color/original-normal strategy at each fraction, and unchanged original. Evaluate every feasible distinct preset. Select minimum training loss. Also report the published FlightHelmet ETC1S/UASTC full-resolution recipe whether feasible or not.
2. **Texture-domain allocation:** decode each candidate to RGBA (KTX via the pinned `ktx extract --transcode rgba32` command), upsample to source dimensions with Lanczos3, and compare consumed channels only. Color/emissive RGB errors are normalized MAE on stored channel values, including alpha when consumed. ORM uses the union of actually consumed R/G/B channels; standalone occlusion/clearcoat uses R. A normal map contributes mean `acos(clamp(dot(normalize(2*sourceRGB-1), normalize(2*candidateRGB-1)))) / pi`, plus alpha error if consumed, averaged across those terms. A zero normal vector maps to (0,0,1). For images serving multiple compatible roles, average the normalized role distortions. Begin with the smallest option for every image and upgrade by largest positive distortion decrease per added byte; error-reducing nonpositive-byte swaps take priority. Recompute after each choice. Ties use image index then option index. Return the best feasible allocation. Evaluate its final configuration in the real renderer. Record its much cheaper computation; do not force it to waste calls.
3. **Render-aware greedy:** start from the best feasible channel-aware preset (or smallest combination if it has lower loss). The initial common charged pool comprises every feasible preset, the smallest combination, and each feasible single-image substitution from that smallest combination. Both greedy and beam receive this pool and are charged for it. Define a single-image effect `d(i,o)=L(start with image i at o)-L(start)`. If the pool exceeds 256, stop and report a protocol feasibility failure rather than truncate by index. At the current state evaluate feasible one-image substitutions in ascending predicted absolute loss `L(start)+sum_i d(i,o_i)`, then byte size, then lexicographic vector. After a complete neighborhood, accept the greatest positive decrease in actual loss per added byte; improving nonpositive-byte substitutions take priority by absolute loss decrease. Stop at local optimum or 256 distinct evaluations. If capped mid-neighborhood, return the lowest-loss evaluated feasible configuration, never merely the last state. Greedy retains every evaluated preset as fallback and gets the same paid sensitivity ordering as beam.
4. **Joint candidate, beam search:** initialize the beam with the four lowest-loss configurations from exactly the same charged pool as greedy. Image impact is `max_o max(0,-d(i,o))`; choose the top three images by impact with index tie-break. Each round proposes all feasible one-image substitutions from each beam state plus all feasible two-image substitutions for the three pairs among those three images. Deduplicate and remove already evaluated states. Rank proposals by the same additive predicted absolute loss as greedy, then bytes then lexicographic vector. Evaluate the first eight proposals (or remaining allowance if smaller), add to the beam, retain the four lowest actual-loss states, tie-breaking by bytes and lexicographic vector. Repeat until 256 evaluations or no new proposal. Return lowest-loss feasible evaluated state. No hidden rendered sensitivities or outcome-specific ordering is allowed. This tests material interactions through actual joint renders; it does not claim beam search is new.
5. **Accessible SpatialPack texture-only recipe frontier:** run the unchanged npm `@spatialpack/core@0.1.0` public `runRecipeSearch` API in a separate comparator environment. For each of its three presets use `searchStrategy: 'grid'`, `searchDecimate: false`, `allowKtx2: true`, and its public `recipeOrdering` hook to retain recipes with `meshopt === false` and no decimation, preserving the approved-geometry scope. Across all three presets evaluate every distinct generated recipe, up to the same 256 ceiling. Its public `qualityGate` hook evaluates the exact common six views and records actual bytes/loss; reject over-budget or structurally incompatible outputs. Select the best feasible rendered loss across all evaluated recipes, giving the comparator the best observed frontier rather than relying on a mismatched size-only winner. This is the actual implementation, not a rewritten approximation, but the comparator is explicitly **texture-only recipe search**, not SpatialPack's complete unconstrained product. Preserve its genuine codec fallbacks and report them. Record all calls/time; if legal/runtime access fails, report the missing comparator and do not claim a competitive pass. Its FSL core is not an implementation dependency or redistributed competing service. No source code is copied into the proposed mechanism.

For a fair strong baseline, the candidate may not use free individual-texture rendered sensitivities: every such configuration counts against its 256 allowance. Texture-only decoding cost is recorded; the inexpensive heuristic is not forced to waste renders. Report performance both against presets and against the best of all four baselines. Failure to beat render-aware greedy is informative even if the simpler render-aware integration beats presets.

## Checks and decisions

Before held-out evaluation: verify original-versus-original pixel equality for repeated deterministic renders; KTX outputs load without unsupported-extension/decoder errors; delivered GLB bytes meet ceilings; material/node/accessor invariants match; every referenced image is present; geometry hash remains identical. Before any real asset reference, validate tiny authored asymmetric orientation, sRGB/data-channel, tangent-normal and alpha controls through the real encode/transcode/browser pipeline. Record whether GPU-compressed formats or RGBA fallback are used; do not claim GPU compression from a file extension. Test a deliberately missing texture and an invalid KTX header to ensure render failures cannot receive a favorable score. These are harness controls, not candidate successes. Record setup failures and all attempts.

Seal a JSON record of every method's final option vector, actual bytes, training loss, call counts and artifact hashes for all cells, then evaluate held-out views. Report all cells, including infeasible/failed ones.

**Technical support for the joint mechanism:** among feasible cells, candidate improves maximum held-out view error at least 15% relative to the strongest baseline in at least two cells from two different assets, while never increasing maximum held-out error more than 10% in any feasible cell. Require an absolute error reduction of at least 0.001 in winning cells so tiny floating-point differences cannot count. All integrity/byte checks must pass. These are prospective effect-size criteria for a small case study, not business proof.

If joint search fails, do not retune against held-out images. A render-aware-greedy result may be described honestly as a narrower finding, but it does not retroactively pass the joint claim. If every method is already near-lossless or preset-optimal at these budgets, report that the tested workflow does not need the new mechanism. No favorable subset or tightened byte budget replaces the frozen primary result.

Independent review should inspect actual GLB/KTX files, run a representative sealed output through the loader and recalculate its byte/error result. A second execution of the same renderer is a replay, not a second renderer or human quality validation.
