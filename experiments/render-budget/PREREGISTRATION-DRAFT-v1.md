# Render-aware KTX allocation — prospective protocol draft

Status: **NOT YET FROZEN; no encoding, rendering or performance evaluation has occurred.** This document proposes a bounded integration experiment. The parent must publish/freeze the final protocol before execution. Clarifications before that freeze are not post-result changes.

## Claim and limits

Can joint rendered-error allocation select per-texture KTX2 encodings with materially better held-out rendered fidelity than competent presets and render-aware greedy allocation under the same GLB-byte ceiling and configuration-evaluation budget?

Business hypothesis: a web 3D production agency could use a reproducible, local batch export and acceptance packet when preparing customer product catalogs. Primary measured outcomes are real deliverable bytes and image error in a named browser renderer. Neither metric establishes human-perceived equivalence, customer savings, runtime speed, cross-device fidelity, or superiority to untested paid software.

## Frozen inputs and exclusion

Use only FlightHelmet, ToyCar, WaterBottle and BoomBox from KhronosGroup/glTF-Sample-Assets commit `c6a6bd13ab2b3c685c7903d03561b8a9392f38b8`, original `Models/<name>/glTF/` files. Source glTF JSON hashes are already in `input-schema.json`; download/hash referenced buffers/images before any rendering. Preserve per-model CC0 license/attribution. Do not use DamagedHelmet. Do not add another asset after results.

Geometry, node hierarchy, UVs, material scalars, texture bindings, sampler modes and animations remain unchanged. Deduplication, mesh quantization/simplification and topology changes are excluded. Images shared across material slots remain shared; a texture used in incompatible color-space roles is retained unmodified and reported rather than guessed. Unsupported extensions or decoder failures fail the affected asset, without substitution.

Budgets are **1,000,000; 2,000,000; 5,000,000 bytes** of the final standalone GLB, including JSON, geometry, KTX data and alignment. These correspond to cited 1–2MB requests and the Khronos product-asset guideline's 5MB recommendation, not budgets chosen after observing gains. FlightHelmet/ToyCar have source nontexture buffers exceeding 2MB; the four resulting small-budget cells are expected infeasible negative cases. An algorithm must return infeasible, never remove geometry or exceed the ceiling. All 12 cells remain reported.

## Actual encodings and runtime

Prospective package pins: glTF Transform core/functions/extensions/CLI 4.5.0; Three.js 0.186.0; Playwright 1.63.0; Sharp 0.35.4; KTX-Software 4.4.2 Darwin arm64 official release. Preserve release/package hashes, actual dependency lock, licenses, Chrome version and renderer backend before experiment. Existing Google Chrome is available. Unpack the official KTX installer locally; no system installation is necessary. If the version cannot run, record failure and return for a prospectively frozen amendment before measuring alternatives. No silent WebP or simulated-image fallback.

For every unique source image, prepare seven options: unchanged original; ETC1S at original/half/quarter dimensions, quality 128, compression level 1; UASTC at original/half/quarter dimensions, level 1, Zstandard level 18. Resize with Sharp Lanczos3, floor dimensions with minimum 4, without upscaling. Correctly declare sRGB for base-color/emissive and linear for noncolor maps. Generate mipmaps consistently. Preserve alpha; use ordinary tool flags rather than custom pixel edits. Record actual commands. Use mipmaps for every compressed option and preserve original sampler rules. If the source sampler does not use mipmaps, retain that sampler; stored but unused mip levels still count toward bytes. Remove byte-identical options only; no outcome-based pruning of encodings.

Three.js GLTFLoader/KTX2Loader must decode/transcode the delivered KTX2 in Chrome and render it using actual material shaders. Record supported GPU compression extensions and each resulting internal format. The same backend renders originals and outputs. Encoding each unique option is common preprocessing, timed and charged equally to all methods. Cache files by image/option hash. Report preprocessing time, render calls, selection time and total cost; no speed claim is planned.

## Views, lighting and metric

Render 512×512, pixel ratio 1, no antialiasing, transparent background composited on constant sRGB 0.18 gray, no shadows, exposure 1, ACES tone mapping, sRGB output. Freeze the exact renderer setup and camera-fitting code before any asset reference render. Use a bounding sphere from original world-space geometry, centered at its center, perspective FOV 35 degrees, camera distance `radius / sin(17.5 degrees) * 1.15`, near/far derived from this sphere. Camera looks at the center. Use original model orientation without hand adjustments.

Selection views: azimuths 0,60,120,180,240,300 degrees; elevation 20 degrees. Selection lighting: a PMREM environment generated from the pinned Three.js `RoomEnvironment` example (intensity 1, rotation zero), ambient white intensity 0.5, and directional white intensity 3 from normalized (1,2,3). The environment prevents metallic materials from becoming an uninformative dark special case. The original and every variant share the identical environment map. Evaluate these six images for every configuration. All algorithms see the same views and metric.

Held-out views: azimuths 30,90,150,210,270,330 degrees; elevation 5 and 40 degrees, producing 12 views. Evaluate each with (A) selection lighting and (B) the same PMREM environment rotated 90 degrees around Y, ambient white 0.5, and directional white intensity 3 from normalized (-3,1,-2), producing **24 held-out images per final output**. Do not render held-out views/lights until every method's choices for all four assets and budgets are sealed. These are prospectively withheld views, not an independent customer asset population.

Primary error: mean absolute sRGB channel difference on pixels where the original foreground alpha exceeds 0.01, after compositing both images on the same gray background. Average the three absolute channel errors and divide by 255. Primary selection loss is the maximum mean error across the six selection views, preventing a good average from hiding one bad view. Report mean and maximum held-out view error, plus the 95th percentile per-pixel error as a secondary diagnostic. Alpha mask and reference come only from the unchanged original. Treat an empty foreground mask as a setup failure. This numerical fidelity proxy is not a human perceptual rating.

## Algorithms and equal-budget comparison

All methods may share the source/encoded option files and deterministic original references. A rendered configuration costs six images, even if a cache makes replay cheap. Each search method receives **128 distinct six-view configuration evaluations per asset per byte budget**; repeated configurations count once within that method. The same configuration evaluated by multiple methods counts toward each method's allowance. Each search receives identical preset candidates, but their evaluations count within its 128 allowance. No method sees another's adaptive results, and held-out images never guide selection. Wall time is separately reported; equal calls are not a claim of equal CPU/GPU time.

1. **Channel-aware preset sweep:** all combinations of one resolution fraction for color images and one for noncolor images (three each), with ETC1S color/UASTC noncolor; plus uniform all-ETC1S and all-UASTC at each fraction, and unchanged original. Evaluate every feasible distinct preset. Select minimum training loss. Also report the published FlightHelmet ETC1S/UASTC full-resolution recipe whether feasible or not.
2. **Texture-domain allocation:** begin with the smallest option for every image. Greedily upgrade by largest reduction in decoded-image RGB MAE per added byte; noncolor channels use equal weighting and normal maps use mean angular error. Use the same finite options and real GLB size. Ties use image index then option index. Evaluate its final configuration in the real renderer. This is an accessible inexpensive texture-space heuristic, not a strawman random allocation.
3. **Render-aware greedy:** begin with the smallest combination, evaluate every feasible one-image substitution in deterministic image/option order, accept the substitution with the greatest positive decrease in six-view maximum loss per added byte (any error-reducing nonpositive-byte substitution takes priority), repeat until no improvement or 128 evaluations. If the cap is reached mid-neighborhood, select the best evaluated feasible configuration. Retain the best preset as a fallback but count any preset renders used within the 128 allowance.
4. **Joint candidate, beam search:** same start and preset fallback. Maintain a beam of four feasible evaluated configurations. Expand each through one-image substitutions, prioritize proposals by previously measured single-image error reduction per byte, and include pair substitutions involving the current three most impactful images so material interactions can be explored. Evaluate proposals until 128 unique configurations; retain the four lowest-loss states, breaking ties by bytes then lexicographic option vector. Always return the lowest-loss feasible evaluated state. Exact proposal ordering, pair-ranking and stopping code must be frozen before the first real render; no asset-specific choices. The intent is a bounded joint search, not a claim that beam search is novel.

For a fair strong baseline, the candidate may not use free individual-texture rendered sensitivities: every such configuration counts against its 128 allowance. Texture-only decoding cost is recorded; the inexpensive heuristic is not forced to waste renders. Report performance both against presets and against the best of all three baselines. Failure to beat render-aware greedy is informative even if the simpler render-aware integration beats presets.

## Checks and decisions

Before held-out evaluation: verify original-versus-original pixel equality for repeated deterministic renders; KTX outputs load without unsupported-extension/decoder errors; delivered GLB bytes meet ceilings; material/node/accessor invariants match; every referenced image is present; geometry hash remains identical. Test a deliberately missing texture and an invalid KTX header to ensure render failures cannot receive a favorable score. These are harness controls, not candidate successes. Record setup failures and all attempts.

Seal a JSON record of every method's final option vector, actual bytes, training loss, call counts and artifact hashes for all cells, then evaluate held-out views. Report all cells, including infeasible/failed ones.

**Technical support for the joint mechanism:** among feasible cells, candidate improves maximum held-out view error at least 15% relative to the strongest baseline in at least two cells from two different assets, while never increasing maximum held-out error more than 10% in any feasible cell. Require an absolute error reduction of at least 0.001 in winning cells so tiny floating-point differences cannot count. All integrity/byte checks must pass. These are prospective effect-size criteria for a small case study, not business proof.

If joint search fails, do not retune against held-out images. A render-aware-greedy result may be described honestly as a narrower finding, but it does not retroactively pass the joint claim. If every method is already near-lossless or preset-optimal at these budgets, report that the tested workflow does not need the new mechanism. No favorable subset or tightened byte budget replaces the frozen primary result.

Independent review should inspect actual GLB/KTX files, run a representative sealed output through the loader and recalculate its byte/error result. A second execution of the same renderer is a replay, not a second renderer or human quality validation.
