# Independent texture-allocation prospective review

Recorded 2026-09-18T11:18:27.444181+00:00. Inputs and hashes: `reviewed-inputs.json`. No encoder, renderer, search algorithm or comparative metric was executed by this reviewer. This draft is not ready to freeze until the search/baseline definitions below are resolved; no result or score is assigned.

## What is already sound

The intended endpoint is actual standalone GLB bytes and a fixed renderer's numerical fidelity, with explicit restrictions on geometry changes and no machine/human-time claims. Four pinned CC0 assets, fixed1/2/5MB budgets, declared naturally infeasible cells, common option files and prospectively withheld view/light combinations give a workable small case study. Sealing all methods' final configurations before any heldout rendering prevents direct view tuning. The heldout views are not independent assets/customers, which the draft correctly states.

PMREM environment lighting is an appropriate precaution for metallic materials. Existing channel-aware presets, texture-domain allocation and rendered greedy search are substantively better comparators than a uniform low-quality preset. A failure of the joint algorithm cannot be renamed a pass for a narrower greedy method.

## Resolve before freeze

**Search algorithm and strong comparator.** Define beam initialization, proposal priority, pair ranking, tie-breaking, duplicate handling, restart and stopping rules completely in prose/pseudocode or frozen implementation before first real render. Three 'most impactful' images needs an exact measured quantity, including nonpositive byte changes and unknown sensitivities. Specify whether any shared preset can seed expansion; do not let the beam expand good preset states while greedy is constrained to an unrelated smallest-image start. Neither method may inherit uncharged adaptive measurements from another method or another budget.

FlightHelmet has15 unique images and up to90 one-image substitutions from a state. With128 evaluations including presets, naive lexical neighborhood scanning may spend almost the whole allowance on one round and a biased prefix of the next. Equal calls alone does not make a deliberately inefficient ordering a strong baseline. Give greedy the same already-paid sensitivity ordering available to the beam, or another frozen competent best-improvement/restart strategy. Preserve actual call counts and report interrupted neighborhoods. Include a suitable pair-swap/simple joint alternative if the candidate's only advantage would be freeing bytes by one downgrade plus another upgrade.

B subsequently identified actual SpatialPack0.1.0 source: it contains TPE-style recipe sampling, rendered-quality hooks, multi-fidelity planning and a perceptual-budget selector. This is close practical prior art, not just a website claim. A lawful separately run strong comparator or a clearly justified comparable implementation is needed before claiming differentiation from current automated tools. Preserve the real method; do not label a weakened preset as SpatialPack. Its bundled core license is FSL1.1 with future Apache conversion, while CLI metadata says MIT. Do not include the restricted core as an OSS component or copy it into a competing implementation. Keep exact source/license pins and comparator integration separate. Internal benchmarking and competing distribution are different acts; the final rights assessment must describe the actual planned use.

**Texture-domain baseline definition.** Different-resolution decoded images cannot be compared until their common sampling grid and reconstruction filter are specified. Normalize angular and channel errors to a declared comparable scalar before ranking upgrades. Use actual consumed channels: packed ORM, normal XYZ, standalone occlusion R, clearcoat R and color RGB are different roles. Include alpha only where the material consumes it, and define multi-role aggregation once. Do not overstate this heuristic as perceptually optimal; the point is a competent inexpensive baseline.

**Encoding semantics.** Freeze exact command options, color/noncolor resize policy and normal-map mip/filter treatment. Assigning linear metadata to a data map is different from applying a color transfer transform to its numeric values. Validate the delivered KTX metadata, not only file decoding. The [KHR_texture_basisu specification](https://raw.githubusercontent.com/KhronosGroup/glTF/main/extensions/2.0/Khronos/KHR_texture_basisu/README.md) requires dimensions divisible by4, appropriate transfer/primaries, allowed orientation/swizzle and compatible alpha handling. The current minimum4/floor wording alone does not ensure divisible dimensions. A missing PNG fallback requires the proper extension declaration. These are format checks, not candidate advantages.

Sharp's default two-dimension resize can crop with its cover mode; freeze a non-cropping policy preserving UV semantics. Specify numerical data handling and color management rather than relying on image metadata inference. See [Sharp resize documentation](https://sharp.pixelplumbing.com/api-resize/). All algorithms must receive the same validated finite options. Existing source samplers and texture transforms must be retained, including ToyCar's scaled UV use and physical material extensions.

**Actual rendering and integrity.** Pin the KTX loader's JS/WASM transcoder assets as well as Three.js and the encoder. [KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html) selects runtime formats based on detected capabilities; record actual compressed internal format or RGBA fallback. No GPU-memory/runtime claim follows from file size. Check extension handling for transmission, clearcoat, sheen and transformed texture coordinates, not just core material slots. Compare an unchanged glTF converted to GLB against the original loader result before testing lossy options, to separate writer/loader changes from compression.

Tiny original asymmetric orientation, known color/data, normal-direction and alpha controls can detect a flipped/swizzled/gamma-shifted path before real selection. A missing-texture/invalid-header control is useful but does not catch a silently wrong valid texture. These are harness controls, not extra favorable benchmark assets. Fix premultiplied versus straight-alpha compositing, screenshot/readback format, gray value interpretation and exposure once. Wait for load/transcode/shader readiness and dispose replaced GPU resources deterministically. Source material inspection finds the chosen real materials are opaque/default-opaque (including physically transmissive ones); do not generalize their result to alpha-cutout or blended asset delivery.

**Budget and feasibility.** A reasonable upper bound is about14,000 selection images plus heldout/control renders, with up to186 compressed texture options before byte-identical deduplication. This is an arithmetic workload estimate, not a measured runtime. Add explicit per-encode, per-render and global wall-time/resource caps with incomplete results marked inconclusive. Do not shrink assets, view counts or search limits after seeing quality results. Record conversion/encoding, decode, shader setup, actual evaluations and selection separately. Free cache reuse must not become free knowledge for one method.

## Planned independent verification after a valid freeze

Hash-check input geometry, image roles, protocol, source, package lock and runtime before inspecting outputs. Audit every failed/infeasible cell. Independently inspect a sealed GLB's exact bytes, KTX header/DFD/mips and material invariants, load it through the actual pinned renderer and recalculate its selection/heldout losses. Inspect all search ledgers for paid call counts, input-only caching and heldout separation. Recompute technical criteria against the strongest applicable baseline, retaining all feasible cells and absolute effect-size thresholds.

This can become a rigorous bounded study, but approval of a future protocol is not a business verdict. Close render-aware optimization prior art materially narrows the possible contribution to a measured per-image allocation/integration benefit under the stated constraints.
