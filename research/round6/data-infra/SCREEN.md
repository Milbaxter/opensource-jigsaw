## R6-D01: why this is worth a bounded next check

The buyer is a team maintaining third-party scientific archives for recurring analysis or downstream delivery. They need not own the upstream archive or be able to rewrite all of it. The service would accept immutable array sources and the team's actual analysis programs/query traces, create a small set of reusable alternate layouts, and leave a reproducible cost ledger including construction and update costs. No human-time saving is claimed.

[OceanHackWeek's practitioner project](https://github.com/orgs/oceanhackweek/discussions/8) explicitly identifies diverse access patterns and limited capacity to rechunk and mirror large externally owned datasets. [The HDF Group sells performance tuning and implementation](https://www.hdfgroup.org/solutions/consulting/). [Earthmover's pricing page](https://earthmover.io/get-started/) identifies an Arraylake platform fee and volume-based Flux query pricing. These establish a paid workflow, not a quoted price or willingness to buy this proposed service.

The integration's useful hypothesis is **less data transferred at equal total storage and equivalent results across several real analyses**, compared with the best practical simple solution. The novelty would be this portable, budgeted deployment and its measured outcome; materialized-view selection, replication and facility-location optimization are established ideas. It is not enough to beat a bad original chunk shape.

### Essential bridge and component necessity

1. VirtualiZarr extracts archive chunk references and metadata without a full archive copy. Its Apache2 code supports existing NetCDF/HDF5/Zarr sources. If input is already suitable native Zarr, this component must be omitted.
2. Xarray provides the unchanged analysis-facing dimensions, coordinates, indexing and CF interpretation. A custom backend must route the actual requested hyperslab; a normal Zarr store cannot silently combine different chunk shapes within one array.
3. Zarr stores selected, lossless alternate blocks and their metadata. Each materialized block is identified by source content/version, variable and exact bounds.
4. OR-Tools selects shared blocks under storage and construction budgets. It is justified only if overlapping requests and mutually useful alternatives create an actual joint decision. If independent per-query choices or a greedy policy match it, omit the solver and reject the claimed cross-field advantage.
5. Transport and instrumentation must count all source reads, local writes, metadata and final-result bytes. Use fsspec only if it is on the actual access path; otherwise use the archive reader's transport hooks. Do not count decorative dependencies.

Discovery repository pins and exact license-file URLs/hashes are in `components.json`; these are not an installed environment lock. Licenses inspected: Zarr MIT, VirtualiZarr Apache2, xarray Apache2, OR-Tools Apache2, fsspec BSD3. Final installed versions and transitive licenses require verification before execution.

### Strong alternatives, not assumed missing features

[Rechunker](https://rechunker.readthedocs.io/en/latest/) writes new chunk layouts using a memory-bounded execution plan. [VirtualiZarr](https://virtualizarr.readthedocs.io/en/latest/) already removes unnecessary copying for archive virtualization. [Icechunk](https://icechunk.io/en/latest/guides/performance/) has concurrent reads, manifest tuning and caching-related optimizations. Its [chunk reindexing](https://icechunk.io/en/latest/guides/moving-chunks/) can move whole chunks through metadata; it explicitly cannot split partial chunks without rewriting payloads. These capabilities are baselines/building blocks, not evidence that suppliers cannot implement workload-aware replicas. TileDB and existing managed array platforms must remain named commercial alternatives.

Required quantitative comparators would include original virtualized source with tuned concurrency; best single/chunked/sharded layout from the same declared search space; best single partial replica; equal-budget LRU/LFU source-chunk cache; greedy marginal-benefit-per-byte replica selection; and query-result memoization. Each gets identical development workloads and a fair tuning budget. Full-copy alternatives may exceed the replica budget, but still report their storage/build-cost/performance frontier rather than hiding them.

WeatherBench2 is another possible source, but its code's Apache2 license must not be confused with dataset terms: its [data guide](https://weatherbench2.readthedocs.io/en/latest/data-guide.html) explicitly warns that individual datasets differ and some are research-only.

Agent B is independently finding unchanged public analysis programs with exact data rights. Such programs can support an honest case-study replay even without production query logs. They do not establish production frequencies. Fixed reproducible notebook queries are legitimate inputs, but manually repeating them to create amortization is not evidence of demand. If all programs perform full scans, or if caching their final outputs solves the workload, this lead should stop before implementation.

## Why the other two are held

[Decord's documented get_batch](https://github.com/dmlc/decord) avoids duplicate frame decoding and manages batch seeking. Its source is Apache2; the last recorded repository push in this screen is July2024. Modern TorchCodec/FFmpeg would also be mandatory competitors. [Mux](https://www.mux.com/docs/pricing/overview) bundles thumbnail capability with storage and separately prices video processing; no competitor-cost number should be repurposed as the price of this scheduler. A rights-cleared Blender film could test frame identity, but would not establish a missing buyer workflow. No media download performed.

[LibPressioOpt](https://github.com/robertu94/libpressio_opt) exposes parameter search and custom metrics. [Compression Safeguards](https://github.com/juntyr/compression-safeguards) explicitly recommends combining its corrections with OptZConfig. That is close implementation-level prior art. Compression Safeguards is MPL2; LibPressioOpt has a custom copyright file requiring exact review rather than assuming an SPDX label. The same NOAA numeric archive could supply inputs after its rights are confirmed. The problem here is missing differentiated workflow evidence, not absence of data or the fact that prior art exists.

**Current recommendation:** preserve R6-D01 as the strongest concrete mechanism, but do not execute yet. The public data/programs are sufficient to design a narrow technical study; lack of production traffic is not itself a blocker. The unresolved issue is whether these few fixed workloads create a meaningful joint decision at all. A direct regional subset plus point-series materialization may fit the storage budget and match the solver. Repeated identical notebook outputs may be cheaper to memoize; known batch analyses may share source reads through one Dask graph. An experiment should include those alternatives and fail honestly if they dominate. Do not manufacture a tiny storage budget, query frequency or arrival order merely to produce an optimization gap.
