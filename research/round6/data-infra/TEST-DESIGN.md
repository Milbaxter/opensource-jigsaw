# Candidate test design — NOT a preregistration

No execution is authorized by this document. Exact public workload programs, data versions, holdout split and comparison configuration remain unresolved. It records prospective design requirements so that implementation cannot quietly define its own favorable task.

Question: Does a budgeted combination of partial alternate layouts reduce measured source transfer for unchanged public array-analysis workflows, after construction cost, more than practical caching and a well-chosen single layout?

Use at most512MB source payload for the initial case study, retaining source metadata, units, missing-value handling and exact array values. Selection must be based on program requirements and access rights, not outcomes. Freeze unchanged analysis code hashes and every allowed adaptation (only source/backend registration and an explicitly disclosed bounded date range if essential). Prefer separate projects for development versus holdout; same-project neighboring slices are not independent projects. Do not invent or weight additional queries to help the optimizer.

Before evaluating, freeze a finite alternate-view generation rule using development program hyperslabs only. Materialize no information selected from heldout query traces. Selected regions may naturally overlap a heldout program, but no boundary may be chosen after reading its performance. Freeze storage budgets (for example5%,10%,20% of source bytes, one primary chosen before execution), maximum construction/solver resource use and cache initialization policy. Count compressed bytes, metadata and duplicate data against every method. Store the original source separately and charge it equally.

Correctness: direct original reader is the oracle; preserve shapes, coordinates, dtypes and missing-value masks. Raw values must be losslessly identical; final floating reductions use preregistered tolerances dictated by unchanged analysis code, not tuned from observed differences. Include array edges, empty selections, reversed coordinate ordering, repeated/fancy indices if supported, source-version mismatch and NaN/fill-value controls. Unsupported index operations must safely fall back, with their cost included.

Baseline set: tuned original/virtualized source; tuned single full layout including sharding when supported; best single partial view; same-budget source-chunk LRU/LFU; greedy marginal savings per storage byte over the exact same candidate views; and cached final query outputs. No full-materialization baseline is falsely declared infeasible without reporting its actual resource frontier. Candidate must share concurrency, codec, source placement and timing boundaries with baselines.

Primary resource candidate metric: total source bytes including construction and the actual fixed development+holdout replay. A meaningful threshold must be chosen before evaluation; a possible target is≥30% lower total bytes than the strongest feasible baseline, with no>10% wall-clock regression and at least1second absolute difference for any timing claim. Storage budget violations or correctness failures fail. A result winning only the recurring phase while losing on total cost is not a pass; report measured breakeven repetition count as a hypothetical, not actual usage. If a replay is inherently one-shot, construction may make the candidate lose legitimately.

Measure actual HTTP range payloads/object reads and local construction writes. A controlled local HTTP server can isolate transfer accounting; its latency is a laboratory condition and must not be called a cloud latency result. Keep real public-source access limited and separate from benchmark traffic. Use fresh processes, native peak RSS, cold/warm cache labels, shuffled order and multiple repeats chosen prospectively. No paid cloud service or external load test.

Expected outputs: machine-readable layout manifest tied to immutable source hashes, readable alternative blocks, replayable adapter, checksums of every query output, full byte/request/build-time records, and cost/performance frontier including failures. If the solver does not beat the greedy baseline, do not claim solver novelty; if no partial views beat simple caching, hold the entire service concept.

Commercial hypothesis after technical success only: an engineering team pays for a recurring workload audit and versioned deployment because its archive and workload change. Testable budget, reachable organizations and a proposed price require a later concrete validation plan. No payment claim follows from a synthetic repetition count, and no outreach is authorized here.

Additional source-driven baseline: when all analysis programs are known together, combine their Dask graphs and share source-chunk reads in one batch. Compare this offline frontier even if a later service targets independently arriving requests. Sequential arrival is a workload assumption requiring explicit registration and cannot be inferred from separate notebook files. Also allow cached supersets to answer contained queries; an exact-key-only result cache would be artificially weak for repeated point series with changing date ranges.

Early feasibility stop before any comparative evaluation: if each documented program's simple regional/point materialization fits jointly within the defensible storage budget, there may be no reason to invoke a joint solver. Preserve that outcome rather than tightening the budget to create scarcity. A technical case-study may still explore public program-derived requests prospectively, but cannot claim observed production traffic or revenue.
