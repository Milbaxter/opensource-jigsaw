# Round10 independent developer/data-infrastructure screen

Recorded 2026-09-18. Source/economic/rights screen only. No prototype, build, benchmark, scheduling simulation, customer outreach, purchase or comparative evaluation. Prior ledgers were searched for these mechanisms; this screen excludes the earlier caching, dbt, FMU, font and document lanes. Five combinations screened; **one conditional source-review lead, zero candidates ready to benchmark or score**.

## 1. Memory-budgeted native build admission — strongest conditional lead

**Combination:** `ninja-build/ninja` ready-task DAG and command execution + compiler process accounting (OS counters; `psutil` is an optional adapter, not a required decorative component) + `google/or-tools` resource-constrained scheduling. Transfer cumulative-resource project scheduling into mixed-memory C++ builds. Product artifact would be an executable admission policy, calibration record, reproducible build report and exported heavy/light-pool fallback, not a dashboard or replacement compiler.

**Observed buyer-origin pain:** [Ninja#1571](https://github.com/ninja-build/ninja/issues/1571) describes a project with80% small-memory jobs and20% large-memory jobs: CPU and RAM constrain different tasks. This is a specific reason a single global concurrency limit can underutilize a machine. The issue remains open. [Ninja#2187](https://github.com/ninja-build/ninja/issues/2187) contains real build failures and practical memory-threshold workarounds. [FlashInfer#3634](https://github.com/flashinfer-ai/flashinfer/issues/3634), opened June2026, describes JIT CUDA compilation exhausting shared system memory; its author reports that a fixed four-job precompile works. These reports establish pain, not a customer's willingness to buy our implementation or an independently reproduced failure.

**Strong alternatives are mandatory.** [Ninja#2605](https://github.com/ninja-build/ninja/pull/2605) is an open unmerged `--keep-free-memory` proposal; its author explicitly notes the threshold is not a complete solution. [FlashInfer#3899](https://github.com/flashinfer-ai/flashinfer/pull/3899) proposes an8GiB-per-job admission estimate, using a guard already present in its AOT path. [LLVM#127364](https://github.com/llvm/llvm-project/pull/127364) adds explicit Flang compile parallelism. Compare calibrated global `-j`, separate compile/link/heavy pools, the threshold guard, and a greedy earliest-ready memory-feasible/critical-path scheduler using identical profiles. A solver beating default OOM or a deliberately low `-j` would establish almost nothing. Stock jobserver integration and dependency correctness must be retained.

**Paid category:** [Incredibuild's AWS Marketplace listing](https://aws.amazon.com/marketplace/pp/prodview-gaxjwt6msh55q) lists a12-month3000core-hour tier at$750, with AWS infrastructure separate. This establishes paid build acceleration, not a price for local memory admission. A service would need repeatable benefit on clean/partially invalidated builds that remain expensive after ordinary compiler caching. Paying to avoid a once-only FlashInfer compilation is a much weaker recurring business than maintaining a team's changing build fleet. No candidate revenue or saved engineering minutes assumed.

**Real inputs and rights:** LLVM's complete public CMake source and generated Ninja graph are usable real build inputs; its license file is Apache2.0 with LLVM exceptions. Ninja and OR-Tools expose Apache2.0 licenses. Exact current source commit pins and API/file evidence are below. A source release is not a measured memory trace. We have not selected favorable translation units or collected profiles. Full LLVM is too large to call a cheap first test; source inspection should select a fixed named component from documented build targets before calibration, with a hard runtime cap. Do not substitute synthetic sleeps/allocated arrays and call them real compiles.

**What would make a decisive bounded test possible:** first establish, without comparative execution, a portable interception point that retains native DAG/output semantics and accounts for compiler descendants. Then preregister two fixed real targets/commits, allowed clean/incremental changes, a calibration-only commit and untouched later commit, total profiling/solver budget and compiler versions. On an isolated Linux runner with enforced cgroup memory ceilings, measure full successful-build elapsed, aggregate memory high-water/OOM events, exit status and output/test equivalence. Charge profiling and solver work; compare a small declared grid of all strong alternatives under the same capacity. Report rebuild break-even count from measured seconds, without inventing build frequency. Stop if calibrated pools/greedy are essentially tied or calibration consumes the gain. Current macOS host is not automatically an isolated Linux memory-cap benchmark. No environment change or execution authorized here.

**Decision: conditional lead for at most a short source/headroom protocol review, not implementation.** The80/20 mixed-resource case supplies a legitimate coupled scheduling hypothesis. Predicting future memory safely, integration with Ninja, held-out drift and greedy-baseline headroom remain unresolved. OR-Tools is justified only if precedence and shared capacities produce a useful joint decision; omit it if simple weighted admission suffices. No scientific novelty claim.

## 2. Setup-aware test-suite packing

**Combination:** `microsoft/playwright` dependency/fixture graph + `buildkite/test-engine-client` timing records + OR-Tools assignment with repeated fixture-setup costs. Deliver a runnable shard plan and observed runner-seconds comparison. [Playwright#29638](https://github.com/microsoft/playwright/issues/29638) shows real dependency/setup expectations interacting with shards. The [Buildkite buyer pricing discussion](https://forum.buildkite.community/t/unhappy-with-test-suite-pricing/4572) and [paid product page](https://buildkite.com/pricing/) establish economic scrutiny of test infrastructure.

**Counterevidence:** [Buildkite's own algorithm description](https://www.buildkite.com/resources/blog/beyond-basic-test-splitting-buildkite-s-approach-to-test-suite-parallelization/) already considers overhead, adaptive file/example granularity, timing estimates and retries. [Its MIT client](https://github.com/buildkite/test-engine-client) is a credible executable baseline, alongside fixture-grouped longest-processing-time and dynamic queues. Public Playwright source/tests are Apache2.0, but a source suite alone does not supply licensed repeated setup-duration histories or a customer workflow. This would need actual instrumented unchanged tests, charged startup, identical isolation and no dropped tests. **HOLD:** no concrete source suite with demonstrated repeated setup bottleneck was identified; generic bin packing is already supplied. No prototype.

## 3. Parquet writer policy under storage and decode budgets

**Combination:** `apache/arrow` exact per-column encodings + `duckdb/duckdb` real query replay + OR-Tools multiple-choice resource allocation. Output a writer configuration and identical-value Parquet artifact, selecting encoding/codec/level across columns under a declared decode-time constraint.

**Pain:** [DuckDB#18984](https://github.com/duckdb/duckdb/issues/18984) is an open report of V2 delta encoding increasing a real attached file's size substantially. The attachment is accessible, but no explicit data redistribution/commercial-use license was established; do not treat issue publication as an open-data grant. [Arrow's API](https://arrow.apache.org/docs/python/generated/pyarrow.parquet.write_table.html) already offers dictionary, codec, level and encoding choices per column. [MotherDuck](https://motherduck.com/product/pricing/) establishes paid analytical compute/storage, not demand for this exact optimizer.

Strong comparisons: current DuckDB and Arrow defaults, file-wide codec/level grid and independent per-column best selection with the same samples. When byte costs are separable, a solver can be unnecessary; measured whole-query decode effects make coupling plausible but also noisy. Public Arrow test data are not representative production workload traffic. **HOLD:** the real failure input lacks verified rights here; no identified repeated buyer budget tradeoff over simple per-column tuning. No synthetic replacement was run, and no proprietary-feature absence is claimed.

## 4. RocksDB compaction parameter evidence service

**Combination:** `facebook/rocksdb` trace/replay and native compaction statistics + its existing Advisor rules + an OSS Bayesian optimizer such as Optuna. Transfer expensive-experiment design into a bounded configuration experiment; deliver a replayable options file and write/read amplification frontier, preserving data correctness.

[RocksDB#13981](https://github.com/facebook/rocksdb/issues/13981) describes degradation at approximately700GB and questions about universal compaction controls. [Native Advisor](https://github.com/facebook/rocksdb/tree/main/tools/advisor) already turns expert rules and logs into configuration suggestions; the baseline must include it, appropriate level/universal variants and a fair grid, not just defaults. [Percona's tuning offer](https://www.percona.com/services/database-performance-tuning/) starts at$11,400 for a scoped database engagement, but its named engine scope is not proof that this price applies to standalone RocksDB. The inspected RocksDB repository includes an Apache license alternative despite GitHub's coarse GPL label.

**HOLD:** the700GB workload/trace is not published with the issue, and `db_bench` generators cannot establish that customer's compaction behavior. Reducing the database to a tiny convenient case can erase the claimed mechanism. The opportunity may be a customer-owned-trace consulting workflow, but no cheap independent public-data comparison is ready. No new optimizer necessary until native Advisor/grid headroom is demonstrated.

## 5. Fragmentation-aware GPU cluster placement

**Combination:** `kubernetes-sigs/scheduler-plugins` placement constraints + public Alibaba production traces + OR-Tools rolling-horizon placement. Deliver placement decisions and replayed admission/utilization evidence, not estimated cloud-dollar savings from arbitrary prices.

Alibaba's [trace program](https://github.com/alibaba/clusterdata) is first-party evidence of a real resource-utilization problem. Its2023GPU trace already comes with [Fragmentation Gradient Descent and multiple strong scheduling baselines](https://github.com/alibaba/clusterdata/tree/master/cluster-trace-gpu-v2023). [Cast AI](https://cast.ai/wp-content/uploads/2025/12/Automated-Kubernetes-Cost-Optimization.pdf) sells automated placement/rightsizing and provides attributed customer statements; this is paid-category evidence, not an independent candidate benchmark. Generic placement is plainly not missing.

**HOLD:** no exact open commercial data grant was found in repository metadata; the README frames use as research/study. Do not relabel GPU packing data as NUMA locality or infer counterfactual application latency from usage aggregates. A scheduler must beat the supplied FGD, best-fit and native policies with identical constraints. Public traces alone do not certify safe live rescheduling. A specific constraint missing from the established baseline was not identified, so no implementation is proposed.
